## Findings

### QA-1 — Critical — Scan lead-matcher can silently discard a genuinely distinct news lead when it shares a portal URL, meeting date, and dollar figure with an unrelated existing lead
- **Category:** correctness / data-integrity (core feature)
- **Route / component:** `src/lib/news/lead-match.ts` `findMatchingLead` (the "killed-lead matcher"), called from `src/lib/news/lead-filing.ts` `fileScanLeads`, called from `performScanWork` (`src/lib/news/desk.ts:636`).
- **Evidence:** Numbered repro, run directly against the shipped matcher function (no server needed — pure function), full transcript saved at `artifacts/05-qa/01-lead-match-adversarial-probe.txt`:
  1. Candidate (freshly AI-returned from a scan): headline `"Council votes on $250,000 library roof repair contract at Sept. 10 meeting"`, `source_urls: ["https://primegov.example/longmont/agenda/2026-09-10"]`.
  2. Existing lead #99 (status `held`, unrelated story): headline `"Council approves $250,000 park irrigation contract at Sept. 10 meeting"`, same `source_urls`.
  3. `findMatchingLead(candidate, [existing#99])` **returns `99`** — a match.
  4. Observed: `extractAnchors` pulls `date:09-10` and `amount:$250,000` from both headlines (2 shared anchors, meeting `ANCHOR_MATCH_MIN_SHARED = 2`), and both headlines share the normalized source URL — so match path 2 (`sharesUrl && sharedAnchorCount >= 2`) fires.
  5. Expected: two headlines naming **different subjects** ("library roof repair" vs. "park irrigation") are two different stories and should both file as separate leads.
  6. Traced into the caller (`src/lib/news/lead-filing.ts:63-76`): on a match, the AI-returned candidate is **never inserted** — the code only bumps `resurfaced_count`/`last_resurfaced_at` on the *existing* row and `continue`s. The candidate's headline, `why`, `topic`, and `evidence` text are discarded with no trace anywhere in the database, no log, no "possible duplicate, review me" state.
- **Why it matters:** This is not a contrived edge case for a civic-agenda scanner. PrimeGov-style portals routinely publish several distinct agenda items under **one page URL** for a single meeting, and municipal contract/grant amounts cluster on round figures ($50k, $100k, $150k, $250k, $500k) — two unrelated items on the same night's agenda coincidentally sharing a dollar figure is a realistic, not a manufactured, collision. When it happens, the newsroom's own scan silently loses a real story with zero signal that anything was dropped — the scan summary reports it as "resurfaced," which reads to the editor as "the killed/held lead about park irrigation came back," not "a second, different story about library repairs was thrown away." The matcher's own design comment (lines 42-67 of `lead-match.ts`) explicitly built the anchor rule to catch same-URL, low-word-overlap rewrites of **the same** story — this repro shows it also catches same-URL, low-word-overlap descriptions of **different** stories that happen to share a date and an amount, which the comment does not anticipate or guard against.
- **Impact scope:** Every newsroom using Scan (the primary lead-discovery flow this product exists to run) against any real civic portal that lists multiple agenda items per page — which is the common case for the PrimeGov/Legistar-style portals this repo is built to poll (`primegov.ts`). Silent, unlogged, no operator-visible error state; a paper could run for months without ever knowing a story was dropped this way.
- **Suggested fix:** Require the two headlines to also clear a minimum floor of `headlinesOverlapEnough`-style topical similarity (or a shared non-generic noun) before the anchor path is allowed to fire, not anchors alone — the anchor path exists specifically for a same-story rewrite that shares almost no words, but "almost no words" and "zero non-generic proper-noun overlap between two different subjects" ("library"/"roof" vs. "park"/"irrigation") should not be treated the same. Alternatively, log/flag anchor-only matches for a human glance rather than silently discarding the candidate's content, so a false merge is at worst reviewable, never invisible.
- **Suggested test:** Add a `lead-match.test.ts` case exactly matching this repro (same URL, same date, same dollar figure, different subject nouns) asserting `findMatchingLead` returns `null`; add a `lead-filing.test.ts` (or extend the existing scan-pass integration test) asserting a second, topically-distinct AI-returned lead on the same source URL/date still produces a new `leads` row rather than only bumping `resurfaced_count`.

### QA-2 — Major — Provider time-budget server fn silently discards an owner's malformed input as a reset instead of rejecting it
- **Category:** correctness / input-validation at the server-fn trust boundary
- **Route:** `saveProviderTimeFn` (`src/lib/news/provider-settings.ts:250`), owner-only writer of `provider_settings.call_ms`, driven from `/desk/ops`.
- **Evidence:** Numbered repro against the real validator chain (`cleanProviderTimeInput` → `saveProviderTime` → `validateProviderSeconds`), transcript below (also runnable directly, no server needed):
  | input `callSeconds` | `cleanProviderTimeInput` output | what `saveProviderTime` then does |
  |---|---|---|
  | `9` | `9` | **rejected**: `"Give it between 10 seconds and 3600 seconds (60 minutes)."` — correct |
  | `3601` | `3601` | **rejected**: same message — correct |
  | `-5` | `-5` | **rejected**: same message — correct |
  | `NaN` | `null` | **silently accepted as a RESET** — writes `call_ms = null`, wiping any stored override back to the shipped default, no error returned |
  | `Infinity` | `null` | same silent reset |
  | `"not-a-number"` (wrong type) | `null` | same silent reset |
  - Root cause: `cleanProviderTimeInput` (`provider-settings.ts:172-180`) does `typeof seconds === "number" && Number.isFinite(seconds) ? Math.round(seconds) : null` — every non-finite or wrong-typed input funnels into the same `null` the Reset button sends, and `saveProviderTime`'s `input.callSeconds === null` branch (line 209) is documented as "what the Reset button sends," not "invalid input."
- **Why it matters:** The one call site of this server fn today (the Server page's number input) can't easily produce `NaN`/`Infinity` from ordinary typing, but this is exactly the class of input QA is asked to probe at the server-fn boundary rather than trust the client to prevent — a future UI regression, a scripted/automated POST, or an owner using the browser devtools to retry a failed request all reach this path directly. The effect is not a crash and not a security bypass, but it is a **silent, undocumented state change**: an owner who has deliberately widened a local model's timeout (the entire feature's reason for existing, per this file's own header comment) can have that override silently wiped back to the shipped default by a malformed request, with the response reading exactly like success (`{ ok: true, settings: [...] }`) and no indication anything was reset.
- **Impact scope:** Owner-only surface, one row per provider; low likelihood of accidental trigger from the UI as it exists today, but a genuine fail-open (validation bypassed into an unrequested behavior) at a boundary this file's own comments say is deliberately "refused, not silently clamped" for out-of-range numbers — the same principle was clearly intended to cover malformed numbers too and does not.
- **Suggested fix:** In `cleanProviderTimeInput`, distinguish "field omitted / explicitly `null`" (Reset) from "a `callSeconds` key was present but is not a finite number" — the latter should produce a `{ ok: false, error: "..." }` from `saveProviderTime`, not fall through to the reset path.
- **Suggested test:** Extend `provider-settings.e2e.test.ts` (or add a unit test next to `cleanProviderTimeInput`) asserting `callSeconds: NaN`/`Infinity`/a non-numeric value produces a validation error, not `ok: true` with the row cleared.

### QA-3 — Minor — `npm run dev` never carries the protective security headers the desk relies on; no doc/comment says so
- **Category:** process/config hygiene (cross-role: also a docs gap)
- **Route:** every route, under the documented local-dev command specifically (`/`, `/login`, `/desk`, `/desk/ops` all confirmed).
- **Evidence:** `artifacts/05-qa/02-built-server-headers.txt`. Running `SECURITY_HEADERS_BASE_URL=http://127.0.0.1:3326 node scripts/security-headers-e2e.mjs` against a clean `npm run dev -- --port 3326` (single verified listener, no stray processes — confirmed via `Get-NetTCPConnection`) fails on the very first check: `"/: X-Frame-Options is \"absent\", expected DENY"`. The same command against a clean `npm run build && node scripts/with-app-env.mjs node .output/server/index.mjs` on the same port **passes** with all five headers present (`X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'; ...`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, `Permissions-Policy`).
- **Root cause, traced:** `vite.config.ts:308-320` only pushes the `nitro()` plugin — which is what auto-registers `server/middleware/*`, including `security-headers.ts` (comment: `"Auto-registers server/middleware/* ... Nitro v3 defaults serverDir to false, so removing this silently unwires ... on deploys"`) — when `command === "build" || isPreview`. `vite dev` (what `npm run dev` runs) takes neither branch, so `security-headers.ts`, `canonical-host.ts`, and `grok-pwa.ts` are all silently inert under the documented dev workflow.
- **Why it matters:** `security-headers.ts`'s own header comment names the exact threat this closes — clickjacking `/desk/ops`, "a page that carries controls that restart the app and the Cloudflare Tunnel on the operator's own Windows machine" — and CI's `security-headers-e2e.mjs` job (`.github/workflows/ci.yml`, `smoke-built`) only ever exercises the **built** server, so this dev/build split has never been caught or flagged anywhere. `SELF-HOSTING.md` correctly tells operators to deploy via `npm run build && npm start`, so the documented production path is not exposed by this. The risk is narrower than it first looks, and I want to be precise about that rather than inflate it: this is a real gap in what a contributor or auditor sees when curling a dev instance (I nearly mis-flagged it as a Critical/Blocker myself before tracing it to a `command === "build"` branch and confirming the built server is clean), not a hole in the shipped product.
- **Suggested fix:** A one-line comment at the top of `server/middleware/security-headers.ts` (or in `AGENTS.md`'s dev-server section) stating these headers are build-only and `npm run dev` intentionally does not carry them, so nobody re-discovers this the way this pass did.
- **Suggested test:** N/A (documentation/comment, not app behavior) — already correctly gated by the CI job that matters (`smoke-built`).

## What's working

- **The scan lead-matcher's core discrimination is sound outside the anchor-only path.** Six adversarial probes beyond the shipped test suite — an unrelated story sharing a generic word and the same source URL, two headlines sharing only paper-furniture words ("council", weekday names), a single shared exact date (correctly held below the documented `ANCHOR_MATCH_MIN_SHARED = 2` bar), a Unicode/emoji headline (no crash, correct match), an empty candidate headline, and a ~35KB pathological headline (no crash, sub-2ms) — all behaved exactly as designed. Only the anchor-plus-shared-URL path (QA-1) produced a wrong answer.
- **The job queue's claim/heartbeat/reclaim design (`src/lib/news/jobs.ts`) is genuinely race-safe, confirmed by reading the mechanism, not just trusting the comments.** `enqueueJob`'s check-then-act is backstopped by a real partial unique index (`desk_jobs_one_open_per_subject`) with `ON CONFLICT DO NOTHING` plus a bounded double-retry, so concurrent enqueues for the same subject coalesce onto one job rather than double-spending a model call (ENG-004, as documented) — the retry logic correctly distinguishes "lost the race" (fine, return the winner's row) from "genuinely nothing exists" (a real thrown error). `executeJob`'s claim is a single conditional `UPDATE ... WHERE status='queued' OR (status='running' AND stale)`, so two drainers racing for the same row safely produce one winner and one no-op, with no `SELECT ... FOR UPDATE` needed. The `claim_token` guard on both the heartbeat and the terminal write correctly prevents a reclaimed-and-restarted execution's original (stale) owner from clobbering the new owner's result.
- **Provider-time-budget validation is correct and well-designed for the numeric-out-of-range case** — 9s, 3601s, and -5s are all refused with a clear, specific error rather than silently clamped, exactly as the module's own header comment promises ("Refused, not silently clamped"). Only the non-numeric/non-finite case (QA-2) falls through that intent.
- **Public reader-facing surfaces are clean and correctly scoped.** `/robots.txt` correctly disallows `/desk`, `/login`, `/api/`, and `/_serverFn/` while allowing everything else and naming the sitemap; `/sitemap.xml` correctly lists only published articles plus the four static reader pages (no desk/login/newsletter leakage), with per-article `lastmod`; `/feed` correctly serves `application/rss+xml` and degrades to an honest "This installation has not been configured yet" channel on a first-run empty desk rather than erroring or serving garbage.
- **The CLI adapter's failure-mode taxonomy (`ai-claude-code.server.ts`) is deliberately and legibly layered**, confirmed by reading the full call path: spawn-failure and CLI-not-found both map to the same actionable `CLAUDE_CLI_MISSING` guidance; a non-zero exit with empty stdout reports the last stderr line or the exit code; a timeout kills the process **tree** (not just the shim — documented and necessary on Windows, where `claude.exe` owns the real session) and reports elapsed time plus bytes-received plus the last stderr line, which is a real improvement over a bare "timed out" (the file's own comment credits a prior incident where a 30-minute failure produced zero evidence); `parseCliEnvelope` cleanly separates "unreadable JSON," "empty result," and "provider-reported error with status code," each with a distinct, specific message. This is the mechanism the (correctly scoped, see Cross-role notes) Automatic fail-over reads to decide whether to hand off.
- **Production build genuinely carries the security headers the desk needs**, verified live against a clean, single-process built server (QA-3 evidence) — `X-Frame-Options: DENY`, a real (if deliberately narrow) `Content-Security-Policy`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`, and a locked-down `Permissions-Policy` all present on `/`, `/login`, `/desk`, and `/desk/ops` alike.
