# Audit Lite — TownReporter 0.6.11 (commit ccf8df4)
**Date:** 2026-09-03
**Scope:** `git diff 3649d9d..ccf8df4` only — data-integrity release: `newsroom_id` threaded through ~33 insert sites, migrations 0033-0036, schema-parity capstone test, source-grep guard test, second-newsroom proof test, `dark-schema-rebuild.test.ts` column-set assertions, and a test-race fix in `dark-model-choice.test.ts`. **Reviewer:** Claude (audit-lite)

## TL;DR
Ship with one caveat, and correct one changelog overclaim before it ships as stated. The `dark.ts`/`desk.ts`/`opinion.ts`/`ops.ts` write paths are genuinely and correctly fixed — a real newsroom id is threaded end-to-end and proven by a real round-trip test. But `investigate.ts` was **not** touched for the two tables it claims (`anomalies`, `artifacts`, `artifact_blobs` all appear in `SCOPED_TABLES` as "fixed"): every insert in that file still hardcodes `DEFAULT_NEWSROOM_ID` (the constant `1`), and no function in that file even accepts a newsroom id to thread. It is internally consistent today (reads use the same hardcoded constant, so nothing user-visible breaks under one newsroom) but it is exactly the class of silent-data-loss bug this release exists to close, for tables the release claims are closed. Separately, the new `schema-parity.test.ts` inherits an existing helper (`pg-admin.ts`) whose default admin URL is the shared dev Postgres on port 5433 — the same port implicated in the prior live-site incident — so running it without `TEST_POSTGRES_ADMIN_URL` pointed elsewhere is a real hazard, even though CI itself is safely isolated.

## Findings

### FINDING-001 Major: `investigate.ts` still hardcodes `DEFAULT_NEWSROOM_ID` on tables the changelog claims are fixed
**Dimension:** Correctness (lens 1 — missed insert)
**Evidence:**
- `src/lib/news/investigate.ts:46` imports `DEFAULT_NEWSROOM_ID` from `./membership.ts` (the constant `1`, `membership.ts:24`) and never imports or threads a real `newsroomId` anywhere in the file.
- Writes hardcoded to `DEFAULT_NEWSROOM_ID` instead of the caller's actual newsroom, in tables that `SCOPED_TABLES` claims are fully fixed: `investigate.ts:1125` (`artifact_blobs` insert — `insert into artifact_blobs (version_id, user_id, newsroom_id, ...) values (..., ${DEFAULT_NEWSROOM_ID}, ...)`), `:1141` (`artifacts` insert), `:1393`, `:1845`, `:1987`, `:2060`, `:2569`, `:2724`, `:2838`, `:2873`, `:2906` (all `anomalies` inserts). The same hardcoded-constant pattern also runs through tables *not* claimed fixed by this release (`artifact_versions` at `:1029`/`:1051`, `source_monitors` at `:1211`/`:1242`, `recurring_baselines` at `:1340`, `entities` at `:2354`/`:2363`) — those are pre-existing and out of this diff's stated scope, cited here only to show the pattern is file-wide, not isolated to the three claimed-fixed tables.
- Every read in the same file is scoped by the same hardcoded constant (e.g. `:1017`, `:1186`, `:1291`, `:1304`, `:1332`, `:1500`, `:1513`, `:1936`, `:1944`, `:2342`, `:2609`, `:2686`, `:2770`, `:2791`), so nothing is *currently* visibly broken — but that is because the file is entirely unaware of newsroom scoping, not because the value is correct.
- None of this file's exported functions (`rememberCapture`, `flagPatternAnomalies`, `researchLoop`, `persistPlan`, `checkBaselines`, `runDueMonitors`, `observeBaseline`, `watchSource`, `seedInvestigation`, `persistDiscovery`, `matchDeadEnds`, `resurfaceDeadEnds`) accept a `newsroomId` parameter — confirmed by grepping every function signature in the file.
- `anomalies` and `artifacts` and `artifact_blobs` are all listed in `scripts/newsroom-scoped-inserts.test.mjs`'s `SCOPED_TABLES` (the "this release's fix verified these are now fully correct" list) and named as fixed in `CHANGELOG.md`'s 0.6.11 entry. The changelog/test docstring *does* carve out an explicit out-of-scope list for `investigate.ts` (`frontier_items, claims, relationships, hypotheses, dead_ends, entities, entity_aliases, entity_matches, investigation_entities, search_attempts, artifact_chunks`) — but `anomalies`, `artifacts`, and `artifact_blobs` are conspicuously **not** on that excluded list, i.e. they are claimed as fixed everywhere, including in this file, and are not.
**Why it matters:** `dark-open.ts`'s `openInvestigationForEditor` (correctly fixed in this diff) now writes the caller's real `newsroomId` onto the `investigations` row. The very next calls in the same flow — `seedInvestigation` → `rememberCapture`/`persistDiscovery` → `artifacts`/`artifact_blobs`/`anomalies` — still file everything under newsroom 1 regardless. The moment a second newsroom exists, an investigation will correctly show under newsroom 2, but its captured evidence, anomaly flags, and dead-end tracking will be silently orphaned under newsroom 1 — invisible to that investigation's own newsroom-scoped reads once (not if) this file is ever newsroom-scoped on the read side too. This is precisely the "editor's work lands in newsroom 1 and vanishes from their own reads" failure mode named in this release's own changelog, in a file this release's own tests claim to have closed.
- Neither new test catches it: `newsroom-scoped-inserts.test.mjs` only checks that `newsroom_id` appears in the INSERT's column list (a static grep) — `investigate.ts`'s inserts do include the column now (from the DDL-alignment half of this commit), just bound to the wrong value. `schema-parity.test.ts` only diffs column *definitions*, not runtime values. `newsroom-scoped-write.proof.test.ts` only exercises the `dark.ts`/`model-request-commit.server.ts` path (`leads`/`drafts`), never `investigate.ts`. There is currently no test that would catch this.
**Fix path:** Thread a real `newsroomId` parameter through `investigate.ts`'s public functions the same way `dark.ts`/`desk.ts` do (mirroring the pattern already used elsewhere in this diff), or — since every one of these functions is always called with an `investigationId` that dark-open.ts already scoped correctly — look the newsroom up once via `select newsroom_id from investigations where id = ${investigationId}` at the top of `rememberCapture`/`flagPatternAnomalies`/etc. and use that instead of the imported constant. Either fix should also add coverage: extend `newsroom-scoped-write.proof.test.ts` (or add a sibling) that exercises `seedInvestigation`/`rememberCapture` for a non-default newsroom, since the existing guard/parity tests structurally cannot catch a wrong *value*.
**Blast radius:** N/A (Major, not Blocker/Critical) — currently silent under the single-newsroom-only posture this release explicitly disclaims turning on ("none of this release turns multi-newsroom on"). Flagging as Major rather than Critical/Blocker on that basis, but it directly undercuts the release's own completeness claim for the three named tables and should not ship silently as "fixed" for `investigate.ts`.

### FINDING-002 Major: new `schema-parity.test.ts` inherits a DB-heavy pattern whose default admin URL is the shared dev Postgres on 5433
**Dimension:** Tests / Runtime (lens 5 — test/prod resource coupling)
**Evidence:**
- `src/lib/news/schema-parity.test.ts:1651-1653` imports `resolveAdminUrl`, `probePostgres`, `run`, `withDatabase` from `../test-support/pg-admin.ts` (pre-existing helper, not new in this diff, but this is a new consumer of it).
- `src/lib/test-support/pg-admin.ts`'s `resolveAdminUrl()`: `return process.env.TEST_POSTGRES_ADMIN_URL ?? "postgres://postgres@127.0.0.1:5433/postgres"` — the fallback is the same port this audit's own hard constraints identify as the shared server that hosts the live paper's data and was starved by exactly this class of DB-heavy test.
- `schema-parity.test.ts`'s `before()` hook (lines ~1734-1783) runs `CREATE DATABASE` twice against that resolved admin URL, replays every migration into one of them via `scripts/migrate.mjs`, and imports/calls ten separate `ensure*Schema()` functions against the other — each opening its own pool connections. `after()` (lines ~1785-1799) terminates backends and `DROP DATABASE`s both.
- The gate is `integrationRequested()` — true only when `TEST_POSTGRES_ADMIN_URL` is set in the environment. CI's `postgres-integration` job (`.github/workflows/ci.yml:163-179`) sets it to a scoped, ephemeral GitHub Actions service container on `127.0.0.1:5432`, not 5433 — CI itself is safe.
- The hazard is local/session execution: any developer or agent session that already has `TEST_POSTGRES_ADMIN_URL` exported (from a previous task, a shell profile, or set-and-forgot) will have `npm test` silently create/drop two databases and open multiple connections against whatever that variable points to — which, unset, is documented in the helper's own comment as "the same value the previous hardcoded constant used," i.e. the real local Postgres on 5433.
**Why it matters:** This is the literal mechanism of the incident this audit was scoped to avoid touching. The opt-in gate is good design, but it is a silent trust boundary with no runtime check that the resolved URL isn't a production/shared instance — nothing stops `TEST_POSTGRES_ADMIN_URL=postgres://postgres@127.0.0.1:5433/postgres npm test` (or an already-exported variable) from repeating the incident on the next promote's pre-flight, or on any contributor machine that happens to have that variable set for an unrelated reason.
**Fix path (isolation):**
1. Reserve 5433 for the live app's actual database and move any local scratch/test Postgres to a different port, so the "same value the previous hardcoded constant used" fallback is no longer also the production port.
2. Add a guard in `pg-admin.ts` that refuses to `CREATE DATABASE`/connect when the resolved URL's host:port matches a configured "do not touch" value (e.g. read from an env var naming the production connection) unless an explicit `--i-know-this-is-shared` override is passed.
3. Prefer a docker-compose (or equivalent) ephemeral local Postgres for these tests so there is no dependency on a shared long-lived server at all, matching what CI already does.
**Blast radius (Major, optional but included given the incident context):**
- **Adjacent code:** `sign-in-throttle.test.ts`, `leave-desk.test.ts`, `search-index.test.ts` already share this same `pg-admin.ts` helper and the same 5433 fallback (pre-existing, not introduced by this diff) — this finding generalizes to all four files, not just the new one.
- **Shared state:** the live paper's own Postgres instance, if 5433 is in fact that instance on this operator's machines.
- **Migration concern:** none for production schema; the risk is purely about test execution stepping on a shared server's connection budget.

### FINDING-003 Minor: allowlist and out-of-scope carve-out are correctly maintained, but their boundary is easy to get wrong silently
**Dimension:** Tests
**Evidence:** `schema-parity.test.ts`'s `ALLOWLIST` (lines ~1710-1729) is well-documented and, on inspection, accurate — every migrations-only table it names (`leads`, `drafts`, `snapshots`, `sources`, `scan_runs`, `articles`, `beat_memory`, `corrections`) is confirmed present only in `migrations/0012_newsroom_appliance.sql` and has no `ensure*` counterpart anywhere in `src/lib/news/*.ts` (verified by grep). `newsroom-scoped-inserts.test.mjs`'s explicit out-of-scope list for `investigate.ts`'s forensics tables is also accurate as far as it goes — but as Finding 1 shows, it does not actually cover every gap in that file (`anomalies`/`artifacts`/`artifact_blobs` are outside the carve-out and still broken).
**Why it matters:** Both lists rely on a human correctly reasoning about scope at write time, and got it right for the tables they named — but the one place they didn't (Finding 1) shipped anyway, silently, past a green test suite. This isn't a defect in the lists as written, but the mechanism (an editable allowlist as the enforcement boundary) is inherently prone to exactly this kind of gap.
**Fix path:** No change required to the lists themselves. Consider a lint rule or CI comment requiring any PR that touches `SCOPED_TABLES`/`ALLOWLIST` to link the specific commit/PR that verified each newly-added table, so future reviewers can audit the claim instead of trusting the docstring.

## What's working
- **The core fix (`dark.ts`, `desk.ts`, `opinion.ts`, `ops.ts`, `lead-filing.ts`, `model-request-commit.server.ts`, `dark-open.ts`) is genuinely correct.** Every production insert site into `leads`, `drafts`, `snapshots`, `sources`, `dark_runs`, `dark_signals`, `dark_promises`, `investigations`, `beat_memory`, `corrections`, `articles`, `anomalies` (in `desk.ts`, as opposed to `investigate.ts`) now threads `owned(context)`/`newsroomId` end-to-end, with `DEFAULT_NEWSROOM_ID` retained as the fallback default everywhere (confirms lens 4 — no hard-error regression risk).
- **`newsroom-scoped-write.proof.test.ts` is a real, non-trivial proof**, not a rubber stamp: it runs the actual `writeStoryForAuthenticatedEditor` commit path for `newsroomId: 2`, asserts the row is absent under `newsroom_id = 1`, and separately re-proves the `newsroomId: 1` default path still works — genuinely tests the failure mode named in the changelog, using PGLite (no shared Postgres needed).
- **Migrations 0033-0036 are idempotent and safe against a populated production DB** (lens 2): every one uses `add column if not exists` / `create table if not exists`, matching the existing style in `migrations/0012_newsroom_appliance.sql`. None of them rewrite or backfill existing rows, so they carry no lock/backfill risk on promote.
- **`DEFAULT 1` is retained on every touched column** (lens 4), both in migrations and in every `ensure*` runtime statement — a missed call site degrades to "silently newsroom 1" (today's status quo), not a hard `NOT NULL` violation. Confirmed no migration in this diff drops or tightens that default.
- **The `dark-model-choice.test.ts` race fix is well-reasoned and correctly scoped.** Checked whether the same fire-and-forget-kick race exists in other test files that call job-enqueuing paths: every other file that calls `enqueueJob` directly already passes `kick: false` (`editorial-result-persistence.test.ts`, `model-request-commit.test.ts`, `write-story-commit.test.ts`, `newsroom-scoped-write.proof.test.ts`), and `dark.preflight.test.ts` deliberately routes around the enqueue step entirely with a documented non-existent-investigation-id trick. `dark-model-choice.test.ts` was the one file exercising the public `startDarkRound`/`startBriefJob` entry points (which kick by default) against a stubbed `runWork` — the fix is targeted correctly, not a band-aid.
- **CI wiring for the new schema-parity test is sound**: it's added to the existing `postgres-integration` job, which already runs against an isolated, ephemeral GitHub Actions Postgres service container — not the shared 5433 dev instance (Finding 2's hazard is about local/uncontrolled execution, not CI).
- **The grep-guard test (`newsroom-scoped-inserts.test.mjs`) has no evasion gaps found**: checked for dynamically-templated `insert into ${...}` table names anywhere under `src/lib` that would bypass its `\w+` table-name regex — none exist.
