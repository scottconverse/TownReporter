## Findings

### FINDING-001 Major: `desk.ts` and `dark.ts` failover wiring has no regression test, old or new
**Dimension:** Tests
**Evidence:**
- `src/lib/news/desk.ts:768-816` (`failOverAndRetry`, the function `performDraftWork` calls on a failed draft — this is the exact code path job 41 hit) is not imported by any `*.test.ts` file in `src/lib/news/`. Confirmed via `grep -rl "failOverAndRetry\|performDraftWork" src/lib/news/*.test.ts` → only `perform-scan-failover.test.ts` matches, and that file exercises `runScanChatWithFailover` (scan-model-run.ts), not `desk.ts`.
- `src/lib/news/dark.ts:1240-1252` (the `performDarkRound` failover block, whose stage-message branch is new in this diff) is not imported by any of `dark-brief.test.ts`, `dark-dials.test.ts`, `dark-model-choice.test.ts`, `dark-schema-rebuild.test.ts`, `dark.open.test.ts`, or `dark.preflight.test.ts` — `grep -rl "performDarkRound" src/lib/news/*.test.ts` returns nothing.
- The one integration test that does exist, `perform-scan-failover.test.ts:64`, only asserts the pre-existing `/sign-in lapsed/` stage message; it was not updated in this diff and does not assert the new `/timed out/` branch (`scan-model-run.ts`'s `switchedBecause` ternary) ever fires.
- `automatic-failover.test.ts` (the only file this diff changed) tests the pure planner in isolation — real, but it never proves the three call sites actually read `plan.reason` and pick the right stage-message branch, or that `desk.ts`'s new `wouldHaveTried` OR-widening (`looksLikeTimeoutOrNoOutput(error) || looksLikeProviderAuthFailure(error)`, `desk.ts:779`) is reachable.
**Why it matters:** This release exists because a previous shipped version of `failOverAndRetry` silently failed to fail over on a timeout — a wiring gap, not a planner gap (the docstring for `automatic-failover.ts` says as much: "nothing else caught it either"). The fix again lives partly in wiring (three call sites each doing their own `plan.reason === "timeout" ? ... : ...`), and that wiring is exactly the part with no test. A future refactor of `desk.ts` or `dark.ts` (or a merge conflict, or a copy-paste error across the three near-identical ternaries) could silently regress to auth-only failover again, or reintroduce a broken message, and CI would not catch it.
**Fix path:** Add at least one integration-style test per call site: (1) `desk.ts` — a `performDraftWork`/`failOverAndRetry` test with injected `PerformDraftWorkDeps` that returns a timeout error from `runReport` and asserts `setStage` was called with `.../ timed out` and the retry ran on the next rung; (2) `dark.ts` — same shape for `performDarkRound`; (3) extend `perform-scan-failover.test.ts` with a timeout-error case asserting the `/timed out/` stage message, mirroring the existing `/sign-in lapsed/` assertion at line 64.
**Blast radius:**
- **Adjacent code:** All three call sites duplicate the same `reason === "timeout" ? \`${label} timed out\` : \`${label} sign-in lapsed\`` ternary independently (no shared helper at this commit — `failoverReasonPhrase`/`failoverNoteSentence` were only extracted later, per HEAD at `24ca11a`). A bug in one copy-paste site wouldn't be caught by testing another.
- **Shared state:** `desk_jobs.stage` (editor-visible mid-run status) and, for the story path, `job.model_choice` — a wrong branch here shows the editor a misleading reason for the switch, not a crash, so it would ship quietly.
- **User-facing change:** The Desk (story drafts) and Dark Desk stage text after any timeout-triggered failover.
- **Migration concern:** None.
- **Tests to update:** `perform-scan-failover.test.ts` (extend); no `desk.ts` or `dark.ts` failover test exists yet to update — one needs to be created for each.

### FINDING-002 Minor: `NO_OUTPUT_RE` is currently unreachable as an independent trigger; docstring overclaims
**Dimension:** Correctness
**Evidence:** `automatic-failover.ts:60-64` defines `NO_OUTPUT_RE = /0 bytes out/i` and frames it in the file's top docstring as a "second, independent trigger, alongside the auth lapse." But the only producer of "0 bytes out" text in the codebase is `ai-claude-code.server.ts:358`: `` `${Math.round(opts.timeoutMs / 1000)}s, ${stdout.length} bytes out` `` — which is always preceded by the literal string `"Claude Code request timed out after "` on the same line (`ai-claude-code.server.ts:359`). `TIMEOUT_RE = /timed out|timeout/i` already matches that same string, so `looksLikeTimeoutOrNoOutput` would return `true` for every real "0 bytes out" case even without `NO_OUTPUT_RE`. Confirmed by `grep -n "bytes out" src/lib/news/*.ts` — every non-test, non-doc hit is on that one line, and it always includes "timed out."
**Why it matters:** Not a functional bug (it's an OR, so it can't cause a false negative), but the code and its own docstring describe a distinct trigger that has no reachable case today. That's a small honesty-of-comments gap, and it's exactly the kind of thing that misleads the next person reading this file into thinking zero-output-without-timeout is already handled — it is not, for any adapter that doesn't spell it exactly this way.
**Fix path:** Either (a) narrow the docstring to say the regex is defensive/forward-looking rather than "independent" today, or (b) make it earn its keep: have `ai-codex.server.ts`'s or a future adapter's zero-output-but-not-technically-"timed-out" case also emit "0 bytes out" (or similar) so the two regexes actually cover different real cases.

### FINDING-003 Minor: the timeout regex is duplicated, not shared, between `preflight.ts` and `automatic-failover.ts`
**Dimension:** Correctness
**Evidence:** `preflight.ts:103` (`scanPreflight`) inlines `/timed out|timeout/i` to classify a *probe* result's `kind` as `"timeout"`. `automatic-failover.ts:59` independently defines the identical pattern as `TIMEOUT_RE` to classify a *draft/scan-call* error for failover. Same regex, two source-of-truth locations, no shared export.
**Why it matters:** These two call sites answer conceptually the same question ("does this error text mean the model was reachable but slow?") for two different consumers (pre-run guidance copy vs. post-run failover decision). If a future timeout wording change (e.g., a new adapter uses "deadline exceeded" instead of "timed out") gets added to one regex and not the other, `scanPreflight`'s guidance and `planAutomaticFailover`'s decision would silently diverge — one would treat it as a timeout, the other as `unknown`/no-failover. Low likelihood, low-but-real drift risk; this diff didn't introduce the duplication but it did add a second independent regex (`NO_OUTPUT_RE`) to the same file without addressing it.
**Fix path:** Export `TIMEOUT_RE` (or a `looksLikeTimeoutText` helper) from one module and import it in the other, the same way `looksLikeProviderAuthFailure` is already shared from `preflight.ts` into `automatic-failover.ts`.

## What's working
- **The planner logic is correct and precisely scoped.** `planAutomaticFailover` (`automatic-failover.ts:85-104`) still refuses to touch an editor's explicit model choice, still stops at exactly one hop, and correctly gives timeout priority over auth-shaped wording when a message matches both (`isAuthLapse = !isTimeout && looksLikeProviderAuthFailure(...)`) — verified both by reading and by the passing "auth-shaped wording nearby" test.
- **No double-spend/hang risk from this change.** The underlying Claude Code adapter (`ai-claude-code.server.ts:339-363`, unchanged by this diff) already kills the full process tree via `killTree()` before resolving a timeout error, specifically to avoid "still spending, with nothing left to read its answer" (its own comment). This diff's new failover trigger fires only after that kill has already happened, so a timeout-triggered retry cannot run concurrently with a still-live first attempt. Codex's probe/call timeouts (`ai-codex.server.ts`) are similarly bounded (10s probe timeout, caller-supplied call timeout) — no unbounded-hang path was found.
- **Honest, dated commit trail.** The file's docstring names the exact live incident (job 41, 2026-09-02, second same-day case), quotes the real error text, and explains why the previous version deliberately excluded timeouts — this is a good pattern for future readers and matches the "read history before shipping" standard.
- **Tests that do exist are precise, not padded.** `automatic-failover.test.ts`'s new cases each isolate one behavior (priority ordering, editor-choice exclusion, last-rung exhaustion) rather than one broad smoke test, and all 11 pass against the exact `a41b23c` tree in an isolated worktree run.
- **Docs/version bump is complete and consistent.** `CHANGELOG.md`, `README.md`, `SELF-HOSTING.md`, `docs/editor.md`, `docs/index.html`, `docs/manual.md`, `docs/setup.md`, `package.json`, and `src/lib/version.ts` all agree on 0.6.7 — no stale version references found in the diff.
- **UX dimension does not apply beyond the stage-text change already covered above** — no new UI surface, form, or interactive state was touched.

## Watch items
- The `wouldHaveTried` explain-branch in `desk.ts` (lines ~768-802) now probes the next rung a second time (once inside `planAutomaticFailover`, once again to build the "not ready" explanation) whenever failover doesn't happen. That duplication predates this diff for the auth case; this diff extends it to the timeout case too. Harmless today (ladder is 2 rungs, probes are cheap and bounded), but worth flattening if the ladder ever grows.
- `AutomaticFailoverReason` is a closed 2-value union (`"auth" | "timeout"`) with no `"unknown"` case. That's fine while `planAutomaticFailover` only ever returns non-null for those two reasons, but any future third trigger will need every one of the three call sites' ternaries updated in lockstep — another argument for extracting the shared `switchedBecause` helper mentioned in FINDING-001/003 sooner rather than later (HEAD at `24ca11a` shows this was in fact done later, as `failoverReasonPhrase`/`failoverNoteSentence` — good, but it happened after 0.6.7 shipped without it).
