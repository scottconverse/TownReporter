## Findings

### FINDING-001 Major: "happy path still kills the real child" test doesn't verify a kill happened
**Dimension:** Tests
**Evidence:** `src/lib/news/provider-login.test.ts:495-522` (`it("the happy path still kills the real child this process holds", ...)`). The test spawns a real hung Codex login via `startProviderLogin`, calls `cancelProviderLogin`, and asserts only `assert.equal(cancelled?.status, "cancelled")`. Unlike the three sibling tests in the same `describe` block (`provider-login.test.ts:419-489`), which each call the locally defined `isAlive(pid)` helper (`provider-login.test.ts:412-417`) to prove a dummy process survives, this test never calls `isAlive` on the real child's pid (available as `started.pid`) to prove the child actually died.
**Why it matters:** `patch(id, { status: "cancelled", ... })` in `cancelProviderLogin` (`provider-login.server.ts:551-552`) runs unconditionally after `killTree`, regardless of whether the kill succeeded — `killTree` swallows its own errors (`provider-login.server.ts:322-329`, the `catch { /* already gone */ }` blocks). So this test would still pass green even if a future change broke the kill call entirely (e.g., an accidental `if (false && entry)` or a typo dropping the `killTree` line), silently regressing the exact "does Cancel still kill the real thing" behavior this review was asked to protect. In CI (`ubuntu-latest`), a broken kill here would also leak a hung `fake-codex-cli.mjs --mode hang` process for the life of the job container.
**Fix path:** After `cancelProviderLogin` returns, poll `isAlive(started.pid)` (with a short retry loop — `killTree`'s Windows path fires `taskkill` async/fire-and-forget, but on Linux CI it takes the synchronous `child.kill()` branch, so SIGTERM delivery is near-immediate; a 200-500ms retry loop is enough) and assert it eventually returns `false`. This mirrors the pattern already used three times in the same file.
**Blast radius:** (Major, optional block — included because it's the sole regression guard for the "no regression to working sign-in" requirement.) Adjacent code: no other test exercises this path. Shared state: none beyond the module's own `live` map. User-facing change: none — this is test-only. Migration concern: none. Tests to update: `src/lib/news/provider-login.test.ts`, the one test named above.

### FINDING-002 Minor: sweep comment says "Once per process" but the mechanism is a module-level singleton, not a documented process boundary
**Dimension:** Correctness
**Evidence:** `provider-login.server.ts:203-212` (`sweepStaleProviderLoginsOnStartup` doc comment) and the `startupSweepDone` module-level `let` at line 208. Verified by code walk that ordering is safe (sweep runs synchronously-gated before any `await`, so no two overlapping calls double-run it, and it always fires on the first `ensureProviderLoginsSchema()` call in the process — before `startProviderLogin` ever inserts its own row, per `provider-login.server.ts:395-410`) — this is correct, not a bug. But nothing enforces the assumption in code (e.g., no comment noting that the flag's safety depends on `ensureProviderLoginsSchema` being awaited to completion before its caller does anything DB-visible, or a note that a hot-reload dev server that resets module state without restarting the process would re-run the sweep against its own live rows — a scenario `resetProviderLoginStartupSweepForTest` exists to simulate for tests, but which could theoretically happen for real under Vite HMR of this module in dev).
**Why it matters:** Low real risk (this file is server-only, `.server.ts` suffix, unlikely to be HMR'd while a login is in flight), but it's the kind of implicit invariant that bites during a future refactor of `ensureProviderLoginsSchema`'s call sites.
**Fix path:** Optional one-line comment addition near `startupSweepDone` noting the invariant it depends on ("safe only because every caller awaits `ensureProviderLoginsSchema()` to completion before touching `live`"). Not blocking.

## What's working
- **ENG-06 core fix is real and complete.** Grepped every `killTree(...)` call site in `provider-login.server.ts` (lines 530, 551, 583, 644) — none pass a DB-sourced `row.pid` anymore; all four either come from `entry.child.pid` (guarded by `live.get(id)` presence) or, at line 644, from a `child` still in the closure of the spawn that owns it. The `row.pid` column is still *written* (`provider-login.server.ts:449`, for display) but never *read back* for a kill anywhere in the file.
- **Startup sweep is ordered correctly.** Verified by reading `startProviderLogin` (`provider-login.server.ts:391-410`): `ensureProviderLoginsSchema()` — and therefore the one-shot sweep — always completes before that call's own row is inserted, and the `startupSweepDone` flag is set synchronously before the first `await`, so no concurrent caller can double-fire it or race it against a row this process just created.
- **Test suite is thorough and passes.** Ran `DATABASE_URL="" node --test src/lib/news/provider-login.test.ts` — 30/30 pass, including the new `ENG-06` describe block's four tests: no-kill-on-absent-entry for both cancel and expire, sweep-retires-stale-row-without-kill, and the happy-path regression test (see FINDING-001 for its gap). The no-kill tests use a genuinely clever proof technique: they spawn a real dummy OS process, point a DB row's `pid` at it without registering it in the module's `live` map, and assert the dummy survives — this is a much stronger proof than mocking `spawn`, since `node:child_process`'s `spawn` export can't be mocked (module comment at `provider-login.test.ts:381-391` explains why).
- **TES-01 walks are real and model-free, confirmed live.** Read both `scripts/scan-desk-e2e.mjs` and `scripts/sources-desk-e2e.mjs` in full — both use genuine Playwright DOM assertions (`getByRole`, `getByLabel`, `getByText`, `locator(...).count()`), not just page-load checks; both reload after writes to prove persistence over React state; Scan never clicks "Run scan" and Sources never touches a writing model, so neither spends a real model call. Then re-ran both live: built server on a spare port (3436, then a fresh instance on 3437) with `DATABASE_URL=""` (PGLite) and `FAKE_CLAUDE_SIGNED_IN=1` — both walks passed end-to-end against the real running app, and both server processes were torn down cleanly by PID afterward (confirmed via `Get-NetTCPConnection` + port re-check).
- **CI wiring is correct and self-checking.** `scripts/ci-jobs.test.mjs` (`each desk-claiming walk exists and is referenced by CI`) and `scripts/integration-ports-are-unique.test.mjs` (`every integration test file binds its own port`) both pass — the new jobs' ports (3420, 3421) are automatically covered by the latter's dynamic file scan, no static list needed.
- **Docs and version bump are accurate.** `CHANGELOG.md`, `README.md`, `package.json`, and `src/lib/version.ts` are all consistent at 0.6.12, and the changelog's description of the fix matches what the code actually does (checked line-by-line against the diff). `paper.test.ts`'s version-lockstep test passes.

Not a regression, just a pre-existing gap this diff didn't need to touch.
- `sweepStaleProviderLoginsOnStartup` retires stale rows across **all** newsrooms in one process-wide sweep (no `newsroom_id` filter) — correct given PID ownership is process-scoped, not newsroom-scoped, but worth a one-line comment if this file ever grows newsroom-scoped assumptions elsewhere.
