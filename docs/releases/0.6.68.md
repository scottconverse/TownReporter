This release is the **backups and the alerts**. Until now a backup existed only
as a side effect of a promotion: `ops\promote.ps1` was the only file in the
tree that ran `pg_dump`, no scheduled task ran one, and the folder beside the
app held 61 files and about 12.5 GB with nothing pruned and nothing on the
second drive. This release makes the backup its own job, gives it a second copy
on the 8 TB drive, and makes the machine say so when any of it stops being true.

## The rule the owner asked for, and the order it happens in

> Keep ONLY 3 days worth and keep only the latest three on the server disk.
> Keep ALL backups (as long as there's room) on drive D: — an 8 TB disk, half
> empty.

That is one sentence with a dependency in it, and the dependency is the whole
design: **nothing local is deleted until every local file is proved to be on
D:.** The order of operations is fixed and each step is load-bearing.

1. **The dump is checked before it is called a backup.** A file only counts as a
   backup if it passes a completeness check — it opened, it closed, its closing
   marker is the one its opening marker promised, and it is bigger than a floor
   no real dump falls below. A truncated dump is moved aside under its own name
   rather than left wearing a backup's name, and it stops the run.
2. **Every local file not already proved on D: is copied, not just the newest
   one.** The first run has to move sixty-odd files, and a run that only ever
   copied the newest could never catch up after a night the copy failed.
3. **A copy is verified by size and by SHA-256.** It is written as
   `<name>.partial`, hashed there, and only renamed onto the real name when both
   match the source. A bad copy never appears under a backup's name, and a good
   copy already on D: is never replaced by a bad one.
4. **Then, and only then, the local folder is pruned to the newest three.**
5. **If any of that cannot be done, nothing is deleted and an alert is raised.**
   A missing drive, a drive that will not accept a write, a copy that fails its
   check, a local file that is not a complete dump — each one stops the prune,
   each one says which file and why, and none of them is a reason to remove a
   local backup. Nothing is ever deleted from D:. D: is pruned by no code path
   in this release.

A copy that would leave less than 100 GB free on the second drive is refused
rather than filling the drive, and that refusal is an alert — "as long as
there's room" is a limit, so the run keeps the room.

## One backup routine, two places that run it

`ops\lib-backup.ps1` holds the only `pg_dump` call in the tree now. It is run by:

- **The nightly run, driven by the watchdog.** The watchdog already runs every
  five minutes. Once a night, after 2:00 AM local, when the newest backup is
  older than 20 hours, it takes a backup. It skips while an editor job is
  running rather than restarting under one. A lock file means two backups never
  run at once, a run may wait for one in flight, and a lock left by a killed run
  is taken over rather than blocking the feature forever.
- **`ops\backup.ps1`, by hand or from the page.** The same function, the same
  rules. It is also the **Back up now** button on the Control page — safe to
  press while the paper is running. `-Offsite` copies without dumping, for the
  one-time move of everything already in the folder.
- **`ops\promote.ps1`**, which used to own the only dump. It now calls the same
  function, so a promotion and a nightly run cannot drift apart.

The watchdog is the only thing that had to change shape, and it did not gain a
task: this is the task the owner already has, run more often for its own sake.

## The machine says when something is wrong

`ops\lib-alert.ps1` watches six things and puts every one of them in
`logs\alerts.json`, which the Control page reads:

- the desk (port 3000) down for more than 10 minutes;
- the public site down for more than 10 minutes;
- the daily scan failed, or did not run by 8:00 AM when it was scheduled to;
- the last good backup more than 30 hours old;
- the copy to D: failing;
- the second drive short of room.

Each alert **fires once when it starts and once when it clears**. The channels
are the Control page's **Attention** card, a Windows notification, and a phone
push through [ntfy](https://ntfy.sh) — and the push is **off until the owner
turns it on**: it does nothing at all unless `ALERT_NTFY_TOPIC` is set in
`.env`, and the code returns before opening a socket when it is not. Nothing
leaves this machine by default.

The paper-down and site-down alerts wait out a 10-minute grace, because a
restart is not an outage; the others fire on the run that finds them. The
daily-scan state is read read-only from the database, the same way the Control
page's last-scan card reads it.

## The Control page

Three cards are new, or new in what they say:

- **Last backup** — the newest backup on this disk, in 12-hour local time.
- **Copy on D:** — how many copies are on the second drive, when they were last
  checked, and how much room that drive has left.
- **Attention** — every alert currently firing, in the owner's words, or
  **Nothing needs attention**.

Two things about these cards are deliberate. **Looking at the page does not
disturb the machine**: the offsite and alert cards read the reports the runs
write, rather than enumerating a drive that may be a spinning disk that has gone
to sleep. And **no card is green when its probe did not answer**: a missing or
unreadable report, or a run that never recorded a verdict on the copy, reads as
a note, not as OK.

## The watchdog no longer calls a running task a failure

Found by the 0.6.66 reboot test. Task Scheduler reports `LastTaskResult`
`267009` — `SCHED_S_TASK_RUNNING` — while a task is still going. The watchdog
read any non-zero value as a fault, and a start task that was in the middle of
Postgres recovery was declared failed, with a repair logged that had not been
needed. `267009` is now read as **still running**: the watchdog says the start
is still running and is waiting for the database, and it logs no FAILED line
inside the boot grace.

## Compatibility

No existing behaviour is removed and nothing else changes shape. There is **no
migration** in this release and **no new scheduled task, service or program**:
the nightly backup and the alerts ride on the five-minute watchdog the owner
already has, and `ops\backup.ps1` is a script, not a task. The one-time copy of
the backups already on this machine is a person running the script once; it is
not automated here.

The first run on an existing installation will therefore find the sixty-odd
backups already in the folder and move them, one verified copy at a time. That
is by design, and it is the only run that looks like that.
