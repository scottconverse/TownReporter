This release is **a small hotfix for the Queue's batch panel, which kept
showing a finished batch, published stories and all, with no way to put it
away.**

## The batch panel stopped being a log of everything

Under "Draft selected", the Queue's batch panel loaded the newsroom's latest
batch and drew every job in it forever. Once an editor started a batch, its
rows sat there for good — including stories the paper had already printed or
that an editor had since killed, each still carrying a **Redraft** button as
if the work were still open. There was no way to make a finished batch go
away; it just kept rendering under its own heading no matter what happened to
the stories it had drafted.

The panel now drops the rows whose story the paper has already printed or
that an editor has killed, and draws nothing at all once that leaves the
batch empty — a "Batch #3" heading over no rows was its own small lie about
what was left to do. A batch that is still running is shown exactly as it
always was, unaffected by this change. And a finished batch — every item
either printed, killed, or otherwise done — gets a **Dismiss** button that
puts it away for good; the next batch an editor starts is a new row and
shows normally.

`getDraftBatch` now left-joins the lead in the same statement that already
reads the batch's jobs, so every item carries the story's current status from
that one query — no extra round trip per item. A missing lead row reads as a
null status and is kept: the filter names the two states it drops (published,
killed) rather than allow-listing the rest, so a lead that was simply deleted
does not silently vanish from the panel too. Dismissal is one nullable
timestamp on the batch row, set once by the Dismiss button and never cleared;
because it lives on the batch itself, the latest-batch read still returns a
dismissed batch rather than quietly resurfacing an older one, and starting a
new batch always shows normally regardless of what happened to the last one.

Unit tests cover the filter directly — published and killed dropped, open
kept, a null status kept because it means the lead row is gone rather than
printed — the state that reaches the panel from the read, and dismissal
being per batch so the next one still shows.

`scripts/batch-published-panel-e2e.mjs` drives the owner's own path with a
fake OpenAI-compatible endpoint answering the drafts — no real model, no
network. One desk, one Custom AI connection, two leads, one batch, one of the
two stories written and printed from its workbench. Run against 0.6.74 it
fails exactly where the owner did — "the printed story's row was still
listed in the batch panel" — and now the panel must have dropped the printed
row while keeping the open one, and Dismiss must still be holding after a
reload. It declares its own two ports, 3532 for the server and 3533 for the
fake, so the uniqueness test can see them, and CI runs it as its own job,
`batch-published-panel-e2e`, against a plain `npm start` on an empty,
DATABASE_URL-free database.

Commits: 7e0595a7 (the domain read, the migration, dismissal), 0459a013 (the
panel filter and Dismiss button, unit tests), ca522f55 (the CI job and the
end-to-end browser walk).

## What a reader sees

Nothing on the public paper changed. Every change in this release is on the
signed-in editor desk's Queue screen.

## Migrations

**One, additive.** `0104_draft_batch_dismissed.sql` adds a nullable
`dismissed_at timestamptz` column to `draft_batches` and runs on start, the
same as every other migration in this repository. `git diff
34d2d7ea..HEAD --stat -- migrations` (`34d2d7ea` is the 0.6.74 release merge)
shows exactly that one file changed under `migrations/` since the last
release; the ledger moves from `0103_read_hourly.sql` to
`0104_draft_batch_dismissed.sql`.

## Compatibility

No existing behavior is removed and nothing changes shape. A batch that is
still running renders exactly as it did before this release. The new column
is nullable and defaults to unset, so every batch row written before this
release reads as not dismissed and keeps showing until an editor dismisses
it or its own items are all done. No stored shape other than the one new
column changes.

## Limits

**The end-to-end walk runs against one desk, one batch of two leads and a
fake OpenAI-compatible provider** — no real model was called or loaded to
build or check this release. **The fix was proven on an empty,
DATABASE_URL-free database started fresh for the CI job**, not against a
newsroom's existing batch history, so a batch row written by an older
version of the app is exercised only through the migration's own
`add column if not exists`, not replayed end to end.
