This release is **the paper comes back by itself after a reboot**.

## The failure, exactly

At 8:00 PM on 2026-09-25 the machine rebooted. The `\TownReporter` logon task
ran at 8:01 and `LastTaskResult` was `1`. `logs/townreporter.log` had the
script's own start line and then nothing — no `[migrate]` line, no app — and
the public site served 502 until the task was run by hand. Running it by hand
worked.

The two lines that did it were in `ops/start-townreporter.ps1`:

```powershell
$ErrorActionPreference = "Stop"
& node scripts/with-app-env.mjs node scripts/migrate.mjs 2>&1 | Add-Content $appLog
```

In Windows PowerShell 5.1 a **native command's stderr under `2>&1` arrives as an
ErrorRecord**, and with the preference on `Stop` that record is *terminating*:
the pipeline stops and the script dies. At boot Postgres answers the TCP port
before it will accept a query; `migrate` wrote `the database system is starting
up` to stderr, and the logon start died on the first line of it. The port-only
check above it is exactly what let that through — **a listening port is not a
database.**

## What now happens instead

### The wait asks a question

`Wait-TownReporterDatabase` asks Postgres a real query — `psql -tAc "select 1"`
on the connection the install actually uses, or `pg_isready` where a cluster
ships no client tools — for up to **three minutes**, with 1s/2s/3s… backoff
capped at five seconds. What Postgres says while it is not ready goes into
`logs/townreporter.log` in plain words and is written **once per change**, so a
three-minute crash recovery is a handful of lines rather than sixty copies of
one. A cluster with no client tool at all is not a reason to keep the paper
down: the wait says so and goes on to migrations, which have their own retries.

### Migrations cannot be ended by what a child prints

The command is unchanged — same script, same wrapper, same `2>&1` — but the
redirection is now done by **`cmd.exe`**, with stdout and stderr pointed at
files (`boot-migrate.out.log`, `boot-migrate.err.log`) instead of piped into
PowerShell. No PowerShell stream ever carries the child's stderr, whatever the
preference in the calling script is, and the exit code still comes back. The
preference is also flipped to `Continue` for the duration: two independent
reasons the same failure cannot return.

Every line and every exit code lands in the log, marked as stdout or stderr,
and the attempt is **retried three times, ten seconds apart**. If the schema is
still not current after the third, the log says so in plain words — *the
database schema is NOT current after 3 attempts, so the paper was NOT started* —
and the start **exits non-zero** rather than appearing to have served the paper.

### The watchdog reads the task result

**What it did before** (the question this release had to answer): when port 3000
was down, `ops/watchdog.ps1` launched `ops/start-townreporter.ps1` as a detached
process of its own, and **nothing read the logon task's result**. So a logon
task that had already failed produced a watchdog that started the script a
second way and could not see whether that failed either — a start that dies at
boot was retried by hand or not at all.

**What it does now:** it reads `Get-ScheduledTaskInfo -TaskName TownReporter`,
and if port 3000 is down, that task's last run ended non-zero, and the run is
at least **three minutes old**, it runs **that registered task** —
`Start-ScheduledTask -TaskName TownReporter` — after asserting the task still
belongs to this install's start script. Never a second copy of the start;
never a second owner. Inside the three-minute grace it says in the log that the
start is still in progress and leaves it alone, because a task that is merely
still starting is not a fault.

### Redlib can be installed where a task can see it

Redlib installed from inside the app sandbox is redirected by Windows into
`%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\…`. A scheduled task
is not a packaged process, so it does not see that merged view: it looked at the
real path, found nothing, and reported **"not installed here"** while the reader
was on disk.

The install root is now a setting the tasks can read, outside AppData:

```
REDLIB_INSTALL_ROOT=C:\Users\scott\TownReporterTools\Redlib
```

Priority is **environment variable > app `.env` > the old AppData default**.
`ops/redlib.ps1` resolves the root once and passes it to the skill's start
script and to the child process, so both answer the same question. `status.ps1`
and the Control page, when the reader is absent but a copy exists under a
`Packages\*\LocalCache` path, now say that in plain words instead of "not
installed".

`ops\redlib-relocate.ps1 -To <dir>` (default
`C:\Users\scott\TownReporterTools\Redlib`) is the one-time move. It copies
rather than moves, finds the install wherever it really is — `-From`, the
configured root, the MSIX sandbox roots, or the AppData path — rewrites the
absolute paths inside `install.json`, prints the `.env` line to add, and
**never edits `.env` itself**. It refuses to copy out from under a live reader
and refuses an AppData target without `-Force`. It is run by a person; it is not
a scheduled task. **It was not run against the real install.**

## Proving it without a reboot

`scripts/ci-boot-recovery.ps1` runs the real `Wait-TownReporterDatabase` and
`Invoke-TownReporterMigrate` out of `ops/lib-migrate.ps1` — the exact code the
logon start runs between "the port is open" and "serve the paper" — against
`.cmd` stubs in a temp directory:

- a probe that refuses twice (writing `the database system is starting up` to
  stderr, like Postgres in crash recovery) and then answers;
- a probe that never answers, which must end in a plain-words line and a `$false`
  rather than a throw;
- a migrate that fails twice on stderr and then succeeds, **with the caller on
  `Stop`** — the exact conditions of the failure;
- a migrate that never succeeds, which must report rather than throw;
- the old `2>&1` idiom itself, run once, to show it really does die.

It touches no Postgres, no port 5433, the paper, or any other live service. The
ops-scripts suite also covers the new `.env` root in both directions, the
relocator against a fake install (copy, path rewrite, live-reader refusal,
existing-target refusal, `-DryRun`), and the watchdog's boot grace.

## What changed for safety

- **The relocator never moves and never deletes.** It copies with `-Recurse
  -Force`, skips `redlib.pid`, and leaves the source install.json and executable
  intact — proven by assertion, not by intention.
- **It never writes `.env`.** It prints the line; the operator adds it.
- **It refuses a live reader** whose pid file names a running process, rather
  than copying a directory out from under it.
- **Migration failures are loud.** A start that cannot serve the paper exits
  non-zero, which is the signal the watchdog acts on — an honest failure in
  place of a silent 502.
- **The watchdog runs the registered task, not the script.** One owner for the
  start, the same ownership check every other repair uses, and a grace period
  before it acts.

## Migrations

This change adds no migration and no scheduled task. The wait and the migrate
runner live in `ops/lib-migrate.ps1`, dot-sourced by the start script that
already existed; the watchdog gained a branch inside its existing five-minute
run. The version and date in `src/lib/version.ts`, `package.json`, the
CHANGELOG, the README and the doc headers were bumped to 0.6.66 together.

## Known limits

- **The proof is against stubs, not a real crash recovery.** `ci-boot-recovery.ps1`
  proves the *shape* of the failure is closed — a child's stderr no longer ends
  the script, and the wait survives a database that refuses queries — but it
  does not run against a Postgres that is genuinely recovering. The real-boot
  proof is a reboot, which this work deliberately did not perform.
- **The relocator was tested on a fake install in a temp directory.** It has not
  been run against the real Redlib installation; the coordinator runs it. Its
  five cases (copy, rewrite, live refusal, existing target, `-DryRun`) passed.
- **Nothing here was run against the live paper.** No scheduled task was
  changed, and the live checkout was not edited. `ops/redlib-relocate.ps1` was
  not pointed at the real install.
- **The watchdog's boot grace is three minutes** and is measured from the
  task's `LastRunTime`. A machine whose Postgres recovery takes longer than the
  start script's own three-minute wait will still see the start fail first, and
  the watchdog will run the task again after the grace — which is the intended
  behaviour, but it means a very slow recovery is retried rather than waited
  out.
- **A task that has never run reads as year 1899** with `LastTaskResult` 267009
  (`0x41303`), which is not a failure; the watchdog guards on that rather than
  treating a never-run task as failed.
- **Production deployment is not asserted here.** A repository version, a tag,
  or a GitHub release does not establish what the live paper is running.

## Evidence boundary

The source tree and a locally built candidate can prove implementation, tests,
migrations, and package contents. Only the GitHub release page can prove
publication, and only a separately authorized production verification can prove
deployment — including the one that matters most for this release, which is a

facts into another.
