## What changed

### Desk browser 404 exception narrowed

The `desk-flows` browser walkthrough suppressed any console message matching `Failed to load resource.*404` for the entire run, which could hide a missing JavaScript chunk, API route, stylesheet, or image anywhere in the walk. The exception now applies only to the deliberate nonexistent error-page route used to exercise the error-surface desk link. An unrelated 404 fails the walkthrough again, and none of the desk-render or document-navigation assertions were weakened. PR #69.

### Release-record coherence

The v0.6.52 release record and its cross-references were repaired so they agree that the tag, GitHub release, and Windows assets exist, and so relative documentation links resolve. This release carries that cleanup forward; it does not modify the published v0.6.52 release or its assets, and the `v0.6.52` tag remains at `9834e81`. PR #69.

### Transaction-scoped advisory lock for routine-policy bootstrap

`ensureRoutineNoticePolicySchema()` ran `pg_advisory_lock(952052)`, its DDL, and `pg_advisory_unlock(952052)` as three separate pooled queries. Because the connection pool can hand each call a different connection and session-level advisory locks bind to the connection, a turnover between lock and unlock could leave the lock held by an idle pooled connection. Concurrent first saves would then block on that idle connection, exhaust the pool, and hang the server.

The bootstrap now uses `withTransaction` with `pg_advisory_xact_lock(952052)`, which is bound to the transaction's single connection and released automatically at commit or rollback. The schema work runs on the transaction's own SQL handle, and `ensureSchemaOnce` memoization is preserved. The existing concurrent-save test now documents why the old timing-based test could not deterministically prove pool turnover and why the transaction-scoped primitive removes that exposure by construction. PR #70.

### Durable jobs reattach on server startup

Server startup now sweeps durable jobs in `queued` or `running` state and reattaches them through the existing claim-token, heartbeat, and checkpoint machinery:

- Queued jobs become claimable again.
- Running extraction jobs resume from their persisted page, stage, and batch checkpoint rather than rereading completed work.
- A stale `running` row whose process is gone is adopted or requeued honestly instead of remaining stranded. It is never terminated by PID signaling.

The sweep is idempotent and uses the repository's existing transaction and advisory-lock patterns so a job is not double-run. A focused disposable-Postgres suite covers queued claim, mid-batch checkpoint resume without reread, and stale running adoption, and the new test is wired into the `postgres-integration` CI job. PR #71.
