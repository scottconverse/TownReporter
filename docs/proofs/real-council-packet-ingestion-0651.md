# Real public council packet ingestion proof (2026-09-17)

**Environment:** isolated build on `http://127.0.0.1:4400`, database `townreporter_dark_live_20260916`, signed-in test owner. Production was not touched.

**Document:** the real, legally published Longmont City Council Regular Session packet for January 13, 2026, retrieved from the city's own PrimeGov portal:

`https://longmont.primegov.com/Public/CompiledDocument?meetingTemplateId=15247&compileOutputType=1`

`pdfinfo`: 41,472,505 bytes, PDF 1.7, **258 pages**, generated by the city's PrimeGov pipeline. Pages 1-12 carry a real selectable text layer (971-1,563 non-space characters per page); no image-only page was found in the first 40. This is a text packet, not a scan.

**How it was exercised:** the file was uploaded through the real Desk **Write a story** document picker (`Attach documents`) on the isolated build, then a story assignment was filed so the retained document attached to a real story record (isolated `story/8`). No whole-packet sweep was run and no giant OCR billing was incurred.

**What the product reported:**

`Read 12 of 258 pages; completed pages retained. Retry to continue.`

**What the database held afterwards** (`story_documents` for that row):

| Column | Value |
| --- | --- |
| `pages` | 12 |
| `extraction_pages` (durable checkpoints) | 12 page chunks |
| `full_text` | 18,080 characters retained |
| `read_parts` / `total_parts` | 0 / 0 — the evidence-notes pass never ran |
| `detail` | `Read 12 of 258 pages; completed pages retained. Retry to continue.` |

No browser console or page errors were recorded.

**What this proves**

- A real 258-page public council packet uploads through the ordinary document control with its original retained.
- The reader is bounded **per batch**, not to 12 pages total: it stopped at the first batch boundary and said so.
- A successful upload does **not** imply a full read. The product states the exact counts and refuses to claim more.
- Completed pages are durably checkpointed mid-read (`extraction_pages` = 12 chunks) and the retained text survives the partial stop (`full_text` = 18,080 characters), so a later retry resumes from saved work instead of a blank slate.
- Because extraction did not complete, the row is not marked `read` and the evidence-notes pass did not run, so no draft claimed to have read the packet.
- The code path that produced both the label and the resume path is `src/lib/news/story-documents.server.ts` (the partial-extraction branch that writes `status='failed'` with the "completed pages retained. Retry to continue." detail and persists `extraction_pages` per page).

**What this does not prove**

- The *resume* step was not re-run to completion here, because finishing 258 pages would run the evidence-notes pass over every chunk and spend real provider quota on mechanical work. The skip-already-read behaviour is covered by `src/lib/news/story-documents.test.ts`, which asserts a 15-page packet resumes at page 13 without rereading pages 1-12. Live evidence here is the durable retention of the 12 completed pages; unit evidence is the resume arithmetic.
- This document has a selectable text layer. It does not establish image-only or scanned-packet quality, OCR accuracy on poor or rotated scans, or table fidelity.
- It does not establish behaviour for a packet larger than the 20-million-character document-text limit.
- A 258-page packet at this batch size needs many retries to finish; that is honest, not fast.
