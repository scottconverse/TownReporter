**Not proven, and not claimed:** fresh-machine human acceptance of the Windows install; any live cross-provider failover; real image-PDF OCR against a provider; a live Story evidence-check; email delivery; and a line-by-line audit of the remaining documentation set.

**Repaired and re-measured:** the Dark Desk reserve is now held against the hop's second model call as well (`b5b71e4`), so run 7 - same newsroom, model and dig as run 5 - finished every stage including the editor brief. The reserve remains a check before a call rather than a cap on it, so a call that starts just above the line can cross it - run 8's hop-3 selector began at 190.8 s, ran 42.4 s, and left the brief only 596 ms, which timed out. Bounded to one call now, but at dig 4/10 with six verifications the configured work can still exceed the 420 s wall. **Correction to how this should be read:** the product does tell the editor - the live dials copy reads "Signals to verify per round (1-24) A larger limit can take longer and use more model calls. Signals beyond the limit remain unverified and are counted as deferred." - so this is a defaults-and-latency question, not a silent failure. The run stops inside its budget with every completed stage preserved, and the remaining item is whether the shipped defaults are too tight for slow providers.
