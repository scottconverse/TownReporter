Record its tag commit, manifest commit, archive SHA-256, application-CI URL, Windows package/install URL and release URL. Require the tag commit, manifest commit and accepted source SHA to be identical, and require both workflows to be successful for that SHA. Do not ask the owner to transcribe these values and do not continue from placeholders or a draft release.


The GitHub release does not establish what Halo currently serves. `ops\promote.ps1` deploys the current `origin/main`; it has no tag or `-Ref` option. Establish a repository freeze covering the final identity check through promotion, or stop if exact-main identity cannot be held. Preserve the existing scheduled-task setup, automatic-publication configuration, approved sources and source-format settings exactly as stored; do not enable, pause, resume, widen, reinstall or otherwise change them during staging or promotion.

Confirm the documented ownership variables and the actual production and development checkout paths. Stop if the checkout is dirty, ownership is not explicit, the expected PostgreSQL tools are unavailable, or the published `v0.6.34` tag does not resolve to its manifest commit.
2. Fetch without merging. Verify all of these independently: the signed-in repository is `scottconverse/TownReporter`; `git rev-parse v0.6.34^{commit}` equals the manifest commit; `git rev-parse origin/main` equals that same commit exactly (stop if main is newer or different); the GitHub release has exactly the accepted assets; its archive hash equals the manifest SHA-256; and the release-linked application and Windows workflows are successful for that commit. Record the current production checkout SHA as the rollback source SHA and run the existing status command. Before relying on the installed `ops\promote.ps1`, compare it with `git show v0.6.34:ops/promote.ps1`. Review any differences under this deployment authorization and use a safe exact-source local procedure based on the release script and documented ownership rules; stop only if an ownership, data, or rollback risk remains unresolved. Do not assume safeguards from the new release are already present in the old checkout, invent flags, or override a guard. Do not retag or rewrite any published tag.

Treat the clean log, migrated real-data copy, and staged counts together as the restore check; a file-size check alone is insufficient.

Never automatically reset or restore after a partly applied migration, and never delete data merely to make a health check green.

Return one operator receipt that distinguishes: GitHub release identity; backup created; staging result; promotion result; served version/source; story-count preservation; scheduled-task, automatic-publication, and approved-source configuration observed unchanged; rollback materials retained; and any unverified item.
