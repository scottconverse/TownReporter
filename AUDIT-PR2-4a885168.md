# AUDIT of PR2 (database copy + swap-back), commit 4a885168. Auditor: HALO. 2026-10-01, about 6:50 PM Mountain.

## VERDICT: NOT CLEAR. 3 blockers, all confirmed by me on a throwaway Postgres (port 5546). Do not rehearse or roll out until fixed.

Method: 4 read-only DeepSeek workers (AP1 lib front, AP2 lib back, AP3 PowerShell flow, AP4 tests/docs; reports `AP*-findings.md`), then I ran the top claims myself. Nothing touched port 5433 or the live paper.

## B1 [BLOCKER, RAN IT] Recovery cannot swap back in the DEFAULT config
`PROMOTE_ADMIN_DATABASE_URL` unset => admin connection = DATABASE_URL = the live database itself. `swapBack` runs `ALTER DATABASE <live> RENAME`. Postgres refuses to rename the database the session is connected to. I ran swapBack with the admin URL pointing at the live DB: THREW "current database cannot be renamed"; nothing changed. So a failed rollout leaves the half-migrated database in place with no way back, in exactly the config `.env.example` recommends. Copy works in that config (I ran it), so the failure shows only at recovery time. Tests miss it because every test connects the admin to a maintenance database. Fix: the library always connects admin work to the `postgres` maintenance database (or template1) on the same server, whatever the URL says; add a test whose admin URL is the live DB itself.
Source: AP3 F1.

## B2 [BLOCKER, RAN IT] A session on the COPY leaves the paper with NO database under the live name
`swapBack` checks connections to the live DB only. Rename 1 (live -> failed) succeeds; rename 2 (copy -> live) fails when anyone (psql, pgAdmin, pg_dump) is connected to the copy. I ran it: THREW "database ..._prerollout_... is being accessed by other users"; databases afterward: `..._failed_..` and `..._prerollout_..` present, NO live name. The exception escapes and the report of rename 1 is thrown away, so the log never says it happened. Neither retry nor `-RollbackDatabase` can resume that state (they refuse with "no database called <db> to move aside"). Fix: check connections on BOTH databases before rename 1; if rename 2 fails, rename failed back to live at once and report; keep the steps list in the error output; make swap-back resumable from the half state (live missing + failed + copy present => finish with rename 2). The comment at :833 ("at no moment is there no database under the live name") is false and must go.
Source: AP2 F1, F2, F3, F4, F6; AP3 F2.

## B3 [BLOCKER, RAN IT] -Resume can never continue after the copy
`Test-PromoteCopyFreshness` demands copy stamp >= the `stop` step's time. The copy stamp is the RUN START second (`$log.Stamp`); the stop happens later (backup, preflight first). I ran it: stop 41 s after run start => False; only the same second gives True. So `-Resume` at or after `dbcopy` always dies "the copy was NOT taken after the paper was stopped". Fix: judge freshness from the `dbcopy` log step time (or write the copy's real creation time into the `promote-db:` line), not the name stamp. Add a test with a stop later than the run start.
Source: AP4 F1.
