# AU1 — migrations and database code (read-only audit)

Scope: `git diff 32ef34ea f7479574` restricted to `migrations/0109..0114`, `scripts/migrate.mjs`, `scripts/migration-plan.mjs`, and DB access code changed in the diff. Read only: nothing was run, no database was touched, no file in the repo was modified.

Counts: **0 BLOCKER, 0 MAJOR, 2 MINOR.**

Worst finding: **F1** — the daily visitor window rotates on the Node process's *local* calendar day while every row it feeds is written on the database's `current_date`; when the two calendars differ (they differ by hours, not "a few minutes"), one reader can be counted twice inside a single database day, or dropped.

---

### F1 [MINOR] The visitor dedupe window is keyed to the process-local day but the rows it writes are keyed to the database's `current_date`, so a reader is deduped per JS day and counted per DB day.

File: `src/lib/news/stats-visitors.server.ts:101` (window key) and `src/lib/news/reading.server.ts:448-450` (row write) (at f7479574)

Failing case: With the DB session timezone at UTC (Neon's default — `src/lib/db.ts:114` opens `new Pool({ connectionString })` with no `options`/`SET TIME ZONE`, and `git grep` for `SET TIME ZONE` / `timezone` / `process.env.TZ` across `src/` and `scripts/` finds no session-timezone setting) and the server process in America/Denver (the repo's own seeds and e2e runs use `America/Denver`), a reader R is seen at `2026-10-01T03:00Z` → the window's day is still `2026-09-30` (local), R is counted, `visitor_daily('2026-10-01') = 1`. The same R is seen again at `2026-10-01T07:00Z` (local 01:00 on 10-01) → `windowFor` rotates, the handle set is empty, R is counted **again** → `visitor_daily('2026-10-01') = 2` for a day with one reader; the Stats panel prints 2. The opposite direction: R at `2026-10-01T23:30Z` and again at `2026-10-02T01:00Z` (local 19:00 on 10-01, window still on the 10-01 JS day) → the second visit is not counted, so `visitor_daily('2026-10-02')` misses it and its `location_daily` row is never written.

Evidence (read only):
```ts
101:function localDay(now: number): string {
102:  const at = new Date(now);                    // process-local timezone
105:  return `${at.getFullYear()}-${month}-${date}`;
109:function windowFor(now: number): VisitorWindow {
110:  const day = localDay(now);
113:  if (existing && existing.day === day) return existing;
114:  const created: VisitorWindow = { day, salt: randomBytes(SALT_BYTES)..., handles: new Set() };
```
against
```ts
448:    insert into visitor_daily (newsroom_id, day, visitors)
449:    values (${newsroomId}, current_date, 1)        // database session calendar
450:    on conflict (newsroom_id, day) do update set visitors = visitor_daily.visitors + 1
```
The handle is `HMAC(salt, ip|uaClass|window.day)` (`stats-visitors.server.ts:130-132`), so the window's `day` is what decides whether a reader is "new"; the row's `day` is `current_date` at write time. The module docstring at `stats-visitors.server.ts:96-99` claims: *"Storage uses the database's `current_date` … so a server whose clock and database disagree at a boundary rotates a few minutes early or late and counts on the right day either way."* Both halves are wrong for this input: the disagreement between an OS timezone and a DB session timezone is the full UTC offset (6–7 h here), not minutes, and "the right day either way" does not hold — a window rotation in the *middle* of a database day re-counts readers already counted on that day. The docstring's own list of error sources (`stats-visitors.server.ts:48-56`) names restarts, eviction and NAT; it does not name this one, so the number shown to the editor carries an undocumented error in both directions. Confirmed new in this batch: `page_views`/`read_hourly` have no in-memory dedupe set, so no existing counter has this coupling.

Confidence: medium — the mechanism is read directly off the code; whether the *deployed* database's session timezone actually differs from the server process's could not be measured without connecting to a database (read only, and the brief forbids it). The bug is latent-but-unconditional in the code: it fires whenever the two calendars differ.

### F2 [MINOR] `0114` builds its index non-concurrently in the same transaction as the `ALTER TABLE`, so the `ACCESS EXCLUSIVE` lock the alter takes on `capture_events` is held for the whole index build.

File: `migrations/0114_editorial_research_captures.sql:20-22` (at f7479574)

Failing case: On the live database, `capture_events` is the one table in this batch that already exists and has been accumulating rows since `0007`. During `npm run build` — which ends in `db:migrate` (`scripts/migrate.mjs:5`) — while the old server is still serving, any session that touches `capture_events` blocks until this file commits: the Evidence screen's listing (`evidence.ts`), a desk capture insert (`investigate.ts:1837`), and the Dark Desk / research `rememberCapture` path all wait. The wait is not the alter (a nullable `ADD COLUMN` with no default is a catalog update) but the index build on line 22, which must scan the table.

Evidence (read only):
```sql
20:alter table capture_events add column if not exists editorial_request_id integer;
22:create index if not exists capture_events_editorial_request_idx on capture_events (editorial_request_id);
```
and the applier, which wraps the **whole file** plus the ledger row in one transaction:
```js
59:        await client.query("BEGIN");
61:        await client.query(text);          // both statements of 0114
62:        await client.query("INSERT INTO _migrations (name) VALUES ($1)", [name]);
63:        await client.query("COMMIT");
```
PostgreSQL takes `ACCESS EXCLUSIVE` for `ALTER TABLE` and holds it to commit; a non-`CONCURRENTLY` `CREATE INDEX` takes `SHARE`, which conflicts with `INSERT`/`UPDATE`/`DELETE`. Because both statements share one transaction, the `ACCESS EXCLUSIVE` is held across the index build, so even `SELECT`s on `capture_events` are blocked for its duration rather than only writes. Counter-evidence stated openly: this is the repo's established pattern — 91 non-`CONCURRENTLY` `create index` statements exist under `migrations/`, including two on this same table at `0007_forensics.sql:42-43` — so this is not new practice; what is new is that the earlier ones ran against a table that was empty at the time. Blast radius is bounded by the migration running before the new server serves.

Confidence: medium — the lock levels and the single-transaction grouping are certain from the code; the size of `capture_events` on the live 900 MB database was **not** measured (read only, no database access), so on a small table the stall is sub-second.

### F1 [MINOR] Migration 0114 builds an index non-concurrently, taking a SHARE lock on `capture_events` and blocking writes to it for the length of the build

File: `migrations/0114_editorial_research_captures.sql:22` (at f7479574)

Failing case: on a live install whose `capture_events` already holds many rows (the desk
writes one per captured page — `0007_forensics.sql:23`), the `alter table` on line 20
commits, then line 22 runs `CREATE INDEX` (no `CONCURRENTLY`) inside the runner's own
transaction. `CREATE INDEX` takes a `SHARE` lock on `capture_events` for the duration of
the build. A `SHARE` lock conflicts with `INSERT`/`UPDATE`/`DELETE` on that table, so
every desk capture that lands while the index builds blocks until the build commits —
the capture path (`rememberCapture`) stalls rather than failing, and if the build
outlasts the caller's statement timeout the write errors out. Because `migrate.mjs`
applies the whole file in one `BEGIN … COMMIT`, the lock is held for the whole build, and
a retried promote re-runs it (idempotent via `if not exists`, so the risk is the lock,
not data).

Evidence (read only):
```
migrations/0114_editorial_research_captures.sql:20
alter table capture_events add column if not exists editorial_request_id integer;
migrations/0114_editorial_research_captures.sql:22
create index if not exists capture_events_editorial_request_idx on capture_events (editorial_request_id);
```
Why it fails: `CREATE INDEX` without `CONCURRENTLY` is the non-blocking-writes form's
opposite; in PostgreSQL the plain form takes `SHARE` and blocks concurrent DML for the
whole build. The statement is mirrored in `INVESTIGATE_SCHEMA_STATEMENTS`
(`src/lib/news/investigate.ts`) for `schema-parity.test.ts`, so the same non-concurrent
build also runs on the runtime ensure path.

Calibration (why this is MINOR, not MAJOR): (a) `capture_events` is a metadata table —
ids, `source_url`, `observed_at` (`0007_forensics.sql:23`), not the multi-MB artifact
tables — so the build should be short; (b) `if not exists` makes it idempotent, so there
is no data-loss or re-run hazard; (c) this is a systemic repo property, not a regression:
`grep -c CONCURRENTLY migrations/*.sql` finds zero, and `scripts/migrate.mjs` runs each
file inside an explicit transaction where `CONCURRENTLY` is illegal, so the codebase
cannot use the concurrent form without changing the runner. The honest statement is
"this is the one new index in the diff, and it blocks writes to its table while it
builds," not "this migration is unsafe."

Confidence: high that the lock semantics are as stated; medium that the stall is
material on a real install (depends on `capture_events` size, which I did not measure —
no database access in this audit).

### F1 [MINOR] `parseDupCheckReply` falls back to the array index for any entry without an id, contradicting the invariant in its own doc comment, and lets a later entry overwrite an earlier id-keyed verdict.

File: `src/lib/news/dup-check.ts:424` (at f7479574)

Failing case: two pairs are sent, `pairs[0]` = lead A→B, `pairs[1]` = lead C→D, and the model replies with the ids dropped from one entry — exactly the "stuttering model" reply the module's own tests say it tolerates:

```
[{"id":2,"same":true,"why":"same vote"},{"same":false,"why":"different"}]
```

Entry 0 names id 2 → lands on `pairs[1]` → `out.set(pair1.key, same:true)`. Entry 1 has no id → `pairs[index]` = `pairs[1]` again → `out.set(pair1.key, same:false)` overwrites it. The pair the model explicitly named and said WAS the same story ends up recorded `same:false`; `pairs[0]` gets no verdict at all. `lead-filing.ts` then reads that `false` and drops the `possible_duplicate_of` link and the "Possible duplicate · compare" chip the word rule had earned — the duplicate is published on the word "no" of an entry about a different pair. The mirror case is a false merge: an id-less entry the model reordered or emitted for another pair lands on whatever occupies that index, and a `same:true` there links a candidate to a story that is not its duplicate.

Evidence (read only):

```ts
// dup-check.ts:424
const pair = numericId != null ? byId.get(numericId) : pairs[index];
```

against the doc comment three lines above it:

```
 *   ... an entry that NAMES an id which is no pair that was
 *   sent is dropped too, rather than falling back to its position in the array:
 *   ... The positional fallback is only for a reply with NO ids at all.
```

The first half of that sentence is implemented: `numericId != null && byId.get(...) === undefined` yields `pair === undefined`, and the next line returns. The second half is not: `pairs[index]` is applied **per entry**, so a single id-less entry in an otherwise id-keyed reply still falls back to its position, and `out.set(pair.key, …)` is last-write-wins with no "already decided" guard. The comment promises a property the code does not have — the exact class of mismatch the same comment says the `key` exists to prevent. A reply with no ids at all (the case the fallback is documented for) is covered by `dup-check.test.ts:353`; a reply with some ids is not, and `dup-check.test.ts:337`'s mixed-reply case only ever exercises entries that all carry ids.

Reachability: requires a model that names ids on some entries and omits them on others — precisely the shape `parseDupCheckReply` is documented and tested to be tolerant of (`dup-check.test.ts:337` "reads a stuttering model's answer anyway", `dup-check.test.ts:353` "matches a reply by position when the model drops the ids it was given"). No prompt instruction or schema enforces all-or-nothing ids.

Confidence: high (the code path is unconditional and the doc comment's claim is false as written). Impact per occurrence is a single chip/link, not data loss — hence MINOR, not MAJOR.

Suggested shape of a fix (not applied — audit only): hoist the fallback to a whole-reply decision — compute `const anyId = entries.some(e => idOf(e) != null)` once, and use `pairs[index]` only when `!anyId` — and/or skip `out.set` for a key already present so a named verdict cannot be overwritten.

### F1 [MAJOR] The Scan page's "Delete pack" is an irreversible, unconfirmed destroy sitting next to "Rename…"

File: `src/routes/desk.scan.tsx:640` (button 640–650; comment 556–566; server `src/lib/news/scan-source-packs.server.ts:194`) (at f7479574)

Failing case: an editor opens Scan → Custom sources, picks the saved pack "City hall regulars"
from the `Saved pack` select, aims for `Rename…` and mis-clicks `Delete pack` (same flex row,
same `.btn` size, differing only by the `danger` class). One press → `deleteScanSourcePack`
runs `delete from scan_source_packs where id = … and newsroom_id = …`, the pack and its rows in
`scan_source_pack_members` are gone, and the only feedback is the success toast "Pack deleted:
the saved set is gone from this list." There is no confirm step and no undo, so the pack cannot
be recovered — only rebuilt by hand, source by source.

Evidence (read only — I did not run it):

```tsx
// desk.scan.tsx:629-650 — the two presses, same row, same size
<button type="button" className="btn" disabled={disabled || rename.isPending}
  onClick={() => { const p = packs.find((x) => x.id === packId); if (p) { setRenameTo(p.name); } }}>
  Rename…
</button>
<button type="button" className="btn danger" disabled={disabled || deletePack.isPending}
  onClick={() => { if (packId) void deletePack.run(() => del.mutateAsync(packId)); }}>
  {deletePack.isPending ? deletePack.pendingLabel : "Delete pack"}
</button>
```

`deleteScanSourcePack` (scan-source-packs.server.ts:199) is an unconditional `delete from
scan_source_packs …` with no soft-delete column and no restore path. The block comment the unit
wrote above these two presses quotes the very finding it is closing — FB0-REPORT.md Table B,
"Delete pack … **SILENT FAIL + NO UNDO + no confirm**" — and then fixes only the first of the
three halves; the comment's own next sentence ("the pack gone, or the reason the server refused
— arrives as a toast") accounts for the silence and says nothing about the undo or the confirm,
which is the "a comment says one thing and the code does another" shape.

Why MAJOR and not higher: the deleted pack is a named *selection* of sources, not the sources
themselves (accepted sources and their scans are untouched), so the loss is user-authored config
rather than news content. Why not MINOR: it is the only press on this screen that destroys
something irreversibly, the desk's own convention for a destroy is confirm-then-undo (the Queue's
`Delete selected` shows "Delete N selected lead(s) and any drafts?" and then offers "Deleted, and
kept for 30 days. Undo" — `desk.queue.tsx:1220-1248` and `1245`, `1283-1294`), and a single
mis-click next to a benign press is the exact input the missing confirmation exists to catch.

Confidence: high (the button, the thunk and the SQL were read end to end; that the delete has no
restore path was read, not assumed).

### F3 [MINOR] After a pack is deleted, the Scan picker still shows it as selected and its "Update pack…" press can never succeed

File: `src/routes/desk.scan.tsx:646` (delete press) and `src/routes/desk.scan.tsx:730` (the label that keys off `packId`) (at f7479574)

Failing case: delete the selected pack (F1). `deletePack`'s mutation only invalidates
`["scan-packs"]` (line 569 → `onSaved` at 257) — nothing sets `packId` back to `null`. `packs`
refetches without the deleted row, so the select at 606–625 now has no option matching
`value={packId}`, but `packId` is still the deleted id, so the picker keeps drawing that pack as
the selected one: `Rename…` and `Delete pack` stay on screen (line 627, `{packId ? …}`), and the
save button still reads **"Update pack with selection"** (line 730). Press the save button now:
it is enabled (line 723 needs only `pickedIds.length`), so the editor names the pack and submits
`{ name, sourceIds: pickedIds, packId: <deleted> }`, and `saveScanSourcePack` runs
`update scan_source_packs … returning id`, gets no row, and throws "That pack no longer exists."
(scan-source-packs.server.ts:150-156). The editor's picked sources are therefore not saved as a
new pack — the press that says "Update pack" can only ever fail until the page is reloaded or
another pack is chosen.

Evidence (read only): the delete path ends at `onSuccess: () => onSaved()` (line 569) and
`onSaved` is `() => { void qc.invalidateQueries({ queryKey: ["scan-packs"] }); }` (line 257); the
only `setPackId(null)` in the file is for leaving Custom scope (line 208), and `setPackId` is
otherwise called only by the select's `onChange` (line 611). Server-side the stale id is refused
honestly rather than silently accepted (so this is stale UI state, not a false success).

Confidence: high for the stale render and the refusal; medium for how often it is reached (it
needs the delete-then-save sequence, but that is one press each).
